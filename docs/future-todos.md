## Self-update download paths (cross-script)

These bullets cover correctness and resilience gaps in the `download_script` family of helpers and their callers across the repo. The 2026-05-05 backport (branch `backport-self-update-fixes`) closed 10 of the gaps tracked in earlier revisions of this file (commits `8746154` through `a557927`). The items below remain deferred for the reasons noted.

- **Map wget exit codes to actionable error messages instead of collapsing all failures.** Most `download_script` wget branches in this repo use `wget -q ... 2>/dev/null` and treat any non-zero exit as a generic "Download failed (network/timeout)". `wget(1)` documented exit codes do distinguish: 4=network, 5=SSL, 6=auth, 8=server (HTTP 4xx/5xx), so a user with an expired credential on a wget-only host gets misdirected to look at their network. Capture the exit code via `wget … || wget_exit=$?` then `case` on it: 4|5 → "Network/SSL error", 6 → "Authentication failed — check token", 8 → "Server error — check token and repo access", * → "Download failed (wget exit $wget_exit)". The 2026-05-05 backport already captures `wget_exit` but only renders it generically — adding the `case` arms is mechanical. Affected sites: every helper library and standalone with a `download_script` body, now including `utils/utils-misc.sh` (library) and its caller `utils/_download-utils-scripts.sh`, added by the 2026-07-17 `utils/` Modular Standalone conversion.

## Config-rewrite sites (atomic-rename gap)

- **Atomic-rename for config-rewrite sites under elevation.** `normalize_trailing_newlines()` in both `utils-sys.sh` and `utils-k8s.sh`, plus `update_config_line()` in both libraries, currently use bare `mktemp` (`/tmp` tmpfs) then cross-FS `mv` to `$file` (often `/etc/...` via `run_elevated`). A SIGKILL or power-loss mid-`mv` can leave a truncated config file. Atomic same-FS rename requires either (a) `mktemp` adjacent to `$file` AND running `mktemp` under the same elevation as the eventual `mv` (complicates the function's calling convention), or (b) writing through a privileged helper that handles both the temp creation and rename atomically. Out of scope for the 2026-05-05 self-update backport; Pattern E3 (bookkeeping-only inline `mktemp` + `TEMP_FILES+=()`) preserved current cross-FS behavior at those sites. Surfaced as a deliberate scope decision in plan `Reviewed: Backport 10 self-update / temp-file / prompt-UX fixes`.

## utils/rsync-two-way.sh

- **Guard the remote-spec host against `ssh`/`rsync` option-injection.** The `REMOTE` argument is parsed by `^([^@]+@)?([^:]+):(.+)$` and the captured host is passed unguarded to the connectivity check `ssh -o BatchMode=yes -o ConnectTimeout=10 "$REMOTE_USER_HOST" "exit"` (`rsync-two-way.sh:181`), which runs BEFORE the user confirmation prompt (`:205`). Shell quoting does not stop *option* injection: a spec whose host begins with `-` (e.g. `./rsync-two-way.sh /local '-oProxyCommand=touch /tmp/x:/p'`) is parsed by `ssh` as an option, so `ProxyCommand` executes a local command with no confirmation — a real local-command-execution path when the tool is driven with an untrusted/pasted spec (low risk for a personal CLI where the user supplies their own args, hence deferred). Pre-existing: byte-identical to the pre-conversion script; the 2026-07-17 Modular Standalone conversion only wrapped the flow in `main()`. Surfaced by the post-implementation review. Future implementer: after parsing, reject option-like hosts (`[[ "$REMOTE_HOST" == -* ]] && { print_error "Invalid host: $REMOTE_HOST"; exit 1; }`) and pass `--` before the positional remotes to `rsync` (`rsync "${OPTS[@]}" -- "$LOCAL/" "$REMOTE"`); for the `ssh` call the leading-`-` guard is the reliable defense.

## utils/rsync-over-tunnel.sh

- **Deeper SSH/rsync option-injection surface (post-`--` `EXTRA`).** The leading-`-` ssh-target guard is in place and the arg parser rejects dash-leading tokens, but everything after `--` (`EXTRA`) is passed verbatim to `ssh` (`source-tunnel`) and `rsync` (`source-transfer`). A crafted `-- -oProxyCommand=...` or hostile rsync flag could still execute commands — the same live class as CVE-2023-51385 / CVE-2025-61984. Deferred because `EXTRA` is a deliberate power-user escape hatch (operator-trust boundary); hardening needs an allowlist/validation design. Track alongside the existing `## utils/rsync-two-way.sh` option-injection item so both rsync scripts are fixed together. Originating: rsync-over-tunnel standardization plan, 2026-07-24.
- **The rsync module is unauthenticated, so any local user on the TARGET can write the destination as root while step 1 runs.** The generated `rsyncd.conf` has `uid = 0`, `read only = false`, and `hosts allow = 127.0.0.1` — which admits every local account on the target, not just the SSH tunnel, because rsyncd cannot distinguish local users by connection. A co-tenant on the target could therefore read or write the destination rootfs as root for the (foreground, supervised) life of the daemon. Not fixed because the only safe design — `auth users` plus a generated secret in a `0600` `/run` file — forces the operator to hand-carry that secret from the target host to the source host, adding a fourth artifact to a deliberately three-step runbook, for a tool whose stated scope is single-user personal machines. Mitigations already in place: `max connections = 1` (a running transfer holds the only slot), loopback-only `address`, `hosts deny = *`, and the daemon is foreground so it exists only while watched. The script header states the single-user constraint. Future implementer: generate a random secret in `cmd_target_tunnel`, write it `0600` under `/run`, add `auth users` + `secrets file` to the config, and give `source-transfer` a `--password-file` / `RSYNC_PASSWORD` path — then decide how the secret crosses hosts without weakening the "nothing persists" property. Originating: post-implementation review finding F5, 2026-07-24.
- **Note for whoever fixes the two option-injection items above: `--` is NOT a verified end-of-options marker for `rsync`.** The `rsync-two-way.sh` entry above prescribes `rsync "${OPTS[@]}" -- "$LOCAL/" "$REMOTE"`. Upstream's own man page (`https://download.samba.org/pub/rsync/rsync.1`, fetched 2026-07-24) documents no `--` handling at all; the only supporting evidence found was generic POSIX advice. `rsync-over-tunnel.sh` therefore guards the *shape* of the path instead (`[[ "$TRANSFER_PATH" == -* ]]`, matching its ssh-target guard) rather than depending on `--`. Verify `--` against the installed rsync before adopting the prescription, or use the same leading-`-` guard.
- **Re-test whether an unentitled Homebrew rsyncd can actually `chroot()` on macOS.** `cmd_target_tunnel` ships `use chroot = no` whenever `DETECTED_OS == macos` and `RSYNC_BIN != /usr/bin/rsync`. That is an *inference* from `com.apple.private.vfs.chroot` being the sole key in Apple's [`rsyncd-entitlements.plist`](https://raw.githubusercontent.com/apple-oss-distributions/rsync/main/rsyncd-entitlements.plist), not a measurement — the 2026-08-05 macOS-support work had no Mac available to confirm it. Future implementer: on a SIP-enabled Mac with Homebrew rsync, hand-edit the generated config to `use chroot = yes` and start the daemon. If it starts, the inference was wrong and the special case should be dropped (it costs real confinement). If it fails with `EPERM`, the shipped behavior is correct — record the measurement here so nobody re-opens it. Either way confirm Apple's `/usr/bin/rsync` still receives `yes`. **Update (2026-08-07):** the second half is now measured — a macOS↔macOS run with Apple's `/usr/bin/rsync` on both ends took the `use chroot = yes` path, the no-chroot consent box never appeared, and the daemon started and served a full transfer, so a chrooted Apple rsyncd demonstrably works. The Homebrew half is still an inference: neither host had a Homebrew rsync, so `use chroot = no` has never run against a live daemon — and neither has the `munge symlinks = no` line, which is emitted only on that branch. Originating: rsync-over-tunnel macOS-support plan, task A6 step 5, 2026-08-05.
- **The 2026-08-05 macOS work was verified with shims, not against real hardware — here is exactly what was and was not exercised.** The ACL/xattr degradation matrix, `require_rsync`'s absolute-path resolution, and the `@RSYNCD:` greeting probe were driven by (a) a fake `rsync` on `PATH` that `cat`s a captured `--version` blob, (b) a `sudo` shim, and (c) a perl one-liner listening on the loopback port and speaking a greeting line. Automated coverage since added in `utils/tests/test-rsync-over-tunnel.sh` covers the parsers, `validate_options`, `compose_transfer_args`, and the generated config. **NOT exercised by any of it:** a real Apple `openrsync` (so the generated `rsyncd.conf` has never been fed to openrsync's parser — see the openrsync directive item below), a real second host (so the tunnel, the daemon handshake, and an actual transfer are unverified end to end on macOS), a real TTY (so the `prompt_yes_no` consent gates on the ACL degradation and the no-chroot path have never been answered interactively on macOS), and `sudo`/`chroot(2)` behaviour under SIP. Future implementer: run the three-step runbook macOS→Linux and Linux→macOS on real hardware and record the result here. **Update (2026-08-07) — macOS↔macOS now runs green, and the first attempt found a real bug.** Both hosts on Apple's `/usr/bin/rsync`: the generated config was fed to openrsync's parser and accepted, the tunnel and daemon handshake worked, both consent gates were answered on a real TTY, `sudo` and `chroot(2)` behaved under SIP, and a 2144-file transfer ran. The bug: `gid = root` does not exist on macOS (gid 0 is `wheel`), so every macOS daemon rejected the connection at attach time with `@ERROR <module>: gid 'root' invalid` — fixed to numeric `uid = 0`/`gid = 0`. **Still not exercised:** the macOS→Linux and Linux→macOS directions (so the cross-platform `-A`/`-X` mapping item below is still untested in anger), the Homebrew-rsync/no-chroot branch, and the payload-level edge cases — the run used a real project directory rather than the appendix's synthetic tree, so symlink preservation (the `/rsyncd-munged/` check), hardlinks, sparse files and cleanup were not individually verified. Originating: rsync-over-tunnel macOS-support plan, task A7 step 4, 2026-08-05; surfaced by the post-implementation review (finding F8) as untracked.
- **Any NEW directive added to the generated `rsyncd.conf` must first be checked against openrsync's parameter table.** openrsync (Apple's `/usr/bin/rsync` on macOS 15.4+) treats an **unknown key as an unrecoverable error**, so one stray directive kills step 1 on every macOS target running the Apple binary. The 16 keys emitted today were verified present in `rsync_daemon_params[]` in `openrsync/daemon_cfg.c` on 2026-08-06 and `build_daemon_config` records that, so this entry is about future additions, not the current set. **Empirically confirmed 2026-08-07:** a real Apple `/usr/bin/rsync` parsed and served the generated config on a macOS target, so the table reading was correct for the `use chroot = yes` variant (15 keys — `munge symlinks` is omitted on that branch and therefore still unproven against a live parser). Note that a key being *accepted* is not the same as its *value* being valid: `gid = root` passed the parser and failed later, at client-attach time, in `daemon_chuser_resolve_name`. Keys openrsync accepts that the script does *not* use, in case they are wanted later: `auth users`, `secrets file` (both needed by the unauthenticated-module item above), `refuse options`, `timeout`, `pre-xfer exec` / `post-xfer exec`, `strict modes`, `incoming chmod` / `outgoing chmod`, `write only`, `filter` / `include` / `exclude`. Future implementer: read the table in [`apple-oss-distributions/rsync`](https://github.com/apple-oss-distributions/rsync), cite the ref you read, and consider a lint that diffs the emitted keys against it so this stops being a manual discipline. Note openrsync's own defaults differ in places worth knowing — `use chroot` defaults to `true` there, and `lock file` to `/var/run/rsyncd.lock`. Originating: rsync-over-tunnel macOS-support plan iteration 3; re-surfaced by the post-implementation review (findings F7 and F34).
- **`-A`/`-X` are lossy between APFS and Linux even when both sides negotiate protocol 30+.** The 2026-08-05 work made the script detect whether ACLs and xattrs are *available*; it does nothing about whether they are *meaningful* across the pair. macOS ACLs are NFSv4-style and do not map onto Linux POSIX ACLs, and the xattr namespaces differ (`com.apple.*` vs `user.*`/`security.*`/`system.*`), so a macOS↔Linux transfer with `-A -X` can silently write metadata the destination cannot interpret — or drop it. Deferred because a correct answer means either a per-direction allowlist (`--filter` on xattr names) or simply refusing `-A`/`-X` on cross-platform pairs, and choosing between those needs real-world testing on a mixed pair. Future implementer: start by capturing what actually survives a round trip in each direction before designing the guard. Originating: rsync-over-tunnel macOS-support plan review, 2026-08-05.
